# P39 — Authoritative Learning-State Application Gateway

## Architecture Overview & Integration Specification (TITAN-KO-039.0 P39)

The **Authoritative Learning-State Application Gateway** (`AuthoritativeLearningStateGateway`) is the controlled, transactional, and idempotent boundary between reconciled learning proposals generated by P38 (`ReconciledLearningStateProposal`) and the authoritative long-term persistence layer owned exclusively by P19 (`ProgressRepository`).

---

## 1. Architectural Role & Boundary Enforcement

The Gateway enforces a strict question:
> *"Can this reconciled proposal be safely, idempotently, and atomically applied to the authoritative P19 learner progress state?"*

```
┌────────────────────────────────────────────────────────────────────────┐
│ P38 ReconciledLearningStateProposal (Domain Value Model)                │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ P39 AuthoritativeLearningStateGateway                                  │
│  ├─ 1. Identity & Structural Validation (non-empty, learner/exam check)│
│  ├─ 2. Idempotency & Duplicate Replay Check (processed session query)  │
│  ├─ 3. Optimistic Concurrency Protection (F_expected == F_actual)       │
│  ├─ 4. No-Op Application (hasStateChanges == false -> zero writes)     │
│  ├─ 5. Transactional Atomic Batch Persistence (applyAtomicBatch)       │
│  ├─ 6. Post-Write Verification & Integrity Reload                      │
│  └─ 7. Deterministic Operation Identity & Canonical SHA-256 Fingerprint │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ P19 ProgressRepository (Authoritative Persistence Layer)               │
│  ├─ getProgress / getProgressForLearner                                │
│  ├─ saveProgress / saveProgressBatch                                   │
│  ├─ isSessionProcessed / markSessionProcessed                          │
│  └─ applyAtomicBatch (All-or-Nothing Commit with Automatic Rollback)   │
└────────────────────────────────────────────────────────────────────────┘
```

### Absolute Boundaries Maintained
* **No Database Ownership**: P39 owns zero tables, zero SQL statements, and zero disk serialization. All state storage is delegated to P19 `ProgressRepository`.
* **Zero SM-2 / Spaced Repetition Logic**: P39 computes zero intervals, next review dates, or repetition counts. Spaced repetition remains isolated to P20 (`ReviewScheduleRepository`).
* **Zero Longitudinal Analytics**: P39 computes zero rolling averages, masteries, or trends. Analytics remain isolated to P23.
* **Zero Question Selection / Composition**: P39 performs zero question fetching, candidate scoring, or test creation. Selection belongs to P33/P34.
* **Zero AI / Non-Deterministic Claims**: P39 contains zero AI models, zero heuristic predictions, zero `DateTime.now()` calls, zero `Random()`, and zero `Uuid()`. All operations are 100% deterministic functions of caller and proposal inputs.

## 2. Core Components & Domain Entities

### `AuthoritativeApplicationDecision` (Enum)
Represents the discrete outcome of attempting to commit a reconciled proposal:
* `applied`: Proposal successfully committed and verified against P19 storage.
* `alreadyApplied`: Proposal duplicate detected (session was already processed); zero duplicate writes performed.
* `noOp`: Proposal contains zero state changes (`hasStateChanges == false`); session recorded, zero progress writes executed.
* `stale`: Optimistic concurrency violation (`proposal.baseStateFingerprint != state.stateFingerprint`).
* `conflict`: Unresolvable state conflict.
* `invalid`: Malformed proposal or input arguments.
* `rejected`: Explicitly rejected proposal.
* `failed`: Persistence IO error or post-write verification mismatch.

### `AuthoritativeApplicationErrorCode` & `AuthoritativeApplicationError`
Immutable error taxonomy with exhaustive error codes:
* `examMismatch`: Proposal exam ID diverges from target state exam ID.
* `learnerMismatch`: Proposal learner ID diverges from target state learner ID.
* `fingerprintMismatch`: Expected base state fingerprint diverges from current state fingerprint.
* `staleState`: State has progressed past base state.
* `alreadyApplied`: Duplicate session detected.
* `invalidProposal`: Structural validation failed.
* `invalidState`: Authoritative state could not be loaded.
* `persistenceFailure`: Atomic batch write threw an exception.
* `verificationFailure`: Post-write state reload did not match proposal expectations.
* `transactionFailure`: Mid-transaction commit aborted.

### `AuthoritativeApplicationResult`
Immutable result value object encapsulating complete audit and operation lineage:
* `operationId`: Deterministic 24-character hex ID computed via `sha256(learnerId|examId|reconciliationId|proposalFingerprint|baseStateFingerprint)`.
* `decision`: Discrete application decision.
* `learnerId` & `examId`: Isolated tenant context.
* `proposalFingerprint`: Source P38 proposal cryptographic hash.
* `previousStateFingerprint`: Cryptographic hash before application.
* `resultingStateFingerprint`: Cryptographic hash after application.
* `appliedChangesCount`: Number of progress records committed.
* `isDuplicate`: Boolean flag indicating replay detection.
* `isSuccess`: Boolean flag indicating non-error state.
* `appliedAt`: Caller-supplied UTC timestamp.
* `provenance`: Lineage metadata from P38.
* `resultingState`: Immutable `AuthoritativeLearnerState` snapshot post-application.
* `error`: Optional error details if failed.
* `fingerprint`: Canonical SHA-256 fingerprint over all result attributes.

## 3. Transaction Semantics & Concurrency Control

### Optimistic Concurrency Protection
Every proposal carries `baseStateFingerprint` ($F_{expected}$). Before applying any mutations:
1. The gateway checks if the session was already applied. If yes, it immediately returns `alreadyApplied` without error.
2. If not applied, the gateway compares $F_{expected}$ against the live state's $F_{actual}$.
3. If $F_{expected} \neq F_{actual}$, an intervening transaction committed between proposal generation and application. The gateway returns `AuthoritativeApplicationDecision.stale` with `fingerprintMismatch` and aborts all writes.

### Idempotent Deduplication
Sessions are registered in `_progressRepository.markSessionProcessed(learnerId, sessionId)`.
* Replaying a previously committed session returns `AuthoritativeApplicationDecision.alreadyApplied`.
* `appliedChangesCount` is strictly `0`.
* Zero writes are executed to P19 progress storage.
* The resulting state fingerprint is preserved identically.
* `operationId` is deterministic and identical across replays.

### Atomic All-or-Nothing Commit
Batch writes are dispatched to `_progressRepository.applyAtomicBatch`.
* In `InMemoryProgressRepository`, snapshots of the progress map and session registry are recorded prior to applying mutations.
* If any error occurs during batch processing, the snapshots are immediately restored, guaranteeing zero partial writes and zero corrupted state.

### Post-Write Verification
Immediately following batch persistence, the gateway reloads the authoritative state directly from P19 (`AuthoritativeLearnerState.fromRepository`).
* It checks that every objective in the proposal has its `attemptCount`, `correctCount`, and `status` accurately represented in persistent storage.
* It verifies that `sessionId` is recorded in the session set.
* If any mismatch is found, the gateway returns `verificationFailure` with `isSuccess = false`.
